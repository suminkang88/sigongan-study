# 1. Role

**WANT**

- 데이터를 분석해 유의미한 인사이트를 도출하는 일
- AI 네이티브로 제품을 설계하고 만드는 일

**CAN**

- 가설 수립 → 데이터 수집 → 간단한 분석 → 인사이트 도출까지의 전 과정
- 난이도가 높지 않은 수준의 AI 네이티브 개발

**AI (CAN'T)**

- 고급 통계 지식이 요구되는 데이터 분석
- 복잡도가 높은 AI 네이티브 개발

# 2. Lexicon 디깅
- 항목당 조사 10분

## 중요도 TOP 10

### 1. Vibe Coding

Andrej Karpathy가 2025년 처음 제안한 용어로, 자연어로 의도를 설명하면 AI가 코드 생성·수정·실행·디버깅까지 처리하는 개발 방식. 개발자의 역할이 "코드를 작성하는 사람"에서 "결과를 검토하고 방향을 조정하는 사람"으로 이동한다. Karpathy 본인도 이를 "프로토타이핑 기법이며 프로덕션 수준 개발과는 구분해야 한다"고 단서를 달았다.

### 2. Agentic Engineering

2026년 Karpathy가 다시 제안한, 바이브 코딩의 다음 단계. AI가 더 유능해지면서 단순 프로토타입을 넘어 실제 제품 수준의 결과물을 만들 수 있게 된 흐름을 가리키며, Plan → Execute → Verify 루프를 AI 에이전트가 수행하고 인간은 구조적 감독(oversight)을 맡는 체계다. 

### 3. Harness 

모델을 제외한 AI 에이전트의 나머지 전부. 툴, 컨텍스트, 프롬프트, 메모리, 훅, 가드레일, 피드백 루프 등을 지칭. 동일한 모델이라도 하니스에 따라 성능 차이가 크게 나기 때문에, 업계에서는 "모델보다 하니스가 더 중요하다"는 말이 통용된다. Claude Code, Cursor 등 AI 코딩 툴의 실체는 대부분 이 하니스 설계다.

### 4. Context Engineering

프롬프트 엔지니어링이 "질문 하나를 잘 쓰는 기술"이라면, 컨텍스트 엔지니어링은 그 한 단계 위, "AI에게 무엇을, 어떤 순서로, 얼마나 보여줄지" 설계하는 작업이다. 작업에 필요한 만큼만 컨텍스트를 제공하는 것(Minimum Viable Context)이 핵심 원칙이며, CLAUDE.md 같은 프로젝트 규칙 파일이 대표 실무 사례다.

### 5. MCP (Model Context Protocol)

Anthropic이 2024년 말 발표하고 이후 Linux Foundation 산하로 이관한 개방형 표준 프로토콜로, AI 에이전트가 외부 툴·데이터베이스·API에 연결되는 방식을 표준화한다. "AI용 USB-C"에 비유되며, 이전엔 서비스마다 커스텀 연동을 만들어야 했다면 MCP 이후엔 한 번의 서버 구현으로 모든 MCP 호환 에이전트가 재사용 가능하다.

### 6. Prompt Engineering 

원하는 출력을 끌어내기 위해 입력 프롬프트의 구조·표현·맥락을 설계하는 작업. 에이전틱 환경에서는 "트릭"보다 구체성과 구조화(역할, 제약조건, 산출물 형식 명시)가 품질을 좌우한다는 것이 중론이다.

### 7. AI Coding Agent 

단일 프롬프트에 응답만 하는 게 아니라, 테스트 실행·파일 읽기·수정·결과 검증까지 다단계로 자율 수행하는 AI. "완결된 루프(run–observe–verify)"를 도는지 여부가 챗봇과 에이전트를 가르는 기준이다.

### 8. Spec-Driven Development

바이브 코딩의 반대편 끝에 있는 접근 방식으로, 기능 명세(Feature Spec)·유저스토리·데이터 엔티티 설계를 먼저 구체화한 뒤 AI에게 구현을 맡기는 방식. 바이브 코딩 ↔ 스펙 기반 개발은 양 극단이 아니라 하나의 스펙트럼으로 이해된다. MVP 초기엔 바이브 코딩 비중이 높고, 프로덕션화 단계로 갈수록 스펙 기반으로 옮겨가는 식.

### 9. RAG (Retrieval-Augmented Generation)

모델이 내부 지식만으로 답하지 않고, 외부 문서·DB에서 관련 정보를 검색(retrieval)해 가져온 뒤 그 내용을 바탕으로 응답을 생성(generation)하는 구조. 최신성이 필요하거나 모델이 학습하지 않은 사내·도메인 데이터를 다룰 때 핵심적으로 쓰인다.

### 10. Context Window 

모델이 한 번에 처리할 수 있는 입력(프롬프트+대화 이력+툴 결과 등)의 최대 길이. 토큰 단위로 측정되며, API 과금도 토큰 단위로 이뤄진다. 윈도우가 꽉 차면 이전 대화를 요약(압축)해서 넣는 과정(Context Compaction)이 필요해진다.

## 📎 그 외 용어 

- **Slop Coding**: 판단 없이 AI 결과를 그대로 배포하는 바이브 코딩의 부정적 버전.
- **YOLO Coding / Prompt-and-Pray**: 검토 없이 AI가 짠 코드를 그대로 실행·배포하는 리스키한 습관.
- **Subagent (서브에이전트)**: 메인 에이전트가 특정 하위 작업을 위임하는 별도 실행 단위.
- **Worktree**: 하나의 저장소에서 여러 브랜치를 동시에 격리된 디렉터리로 작업할 수 있게 하는 Git 기능.
- **Checkpoint**: 에이전트 작업 중 되돌아갈 수 있는 저장 지점.
- **Context Collapse**: 컨텍스트가 과도하게 쌓이거나 오염되어 모델 성능이 떨어지는 현상.
- **Minimum Viable Context**: 작업에 필요한 최소한의 컨텍스트만 제공한다는 설계 원칙.
- **System Prompt**: 매 요청 전에 하니스가 모델에 미리 주입하는 역할·규칙·안전 지침.
- **Token (토큰)**: 모델이 텍스트를 처리하는 최소 단위. 과금·컨텍스트 길이의 기준.
- **Temperature**: 모델 출력의 무작위성(창의성) 정도를 조절하는 파라미터.
- **Hallucination (환각)**: 모델이 사실이 아닌 내용을 그럴듯하게 생성하는 현상.
- **Zero-shot / Few-shot Prompting**: 예시 없이(zero) 혹은 소수 예시를 주고(few) 작업을 요청하는 방식.
- **Chain of Thought**: 모델이 단계별 추론 과정을 거쳐 답을 도출하도록 유도하는 기법.
- **Guardrails (가드레일)**: 에이전트가 허용된 범위를 벗어나지 않도록 거는 제약 장치.
- **Tool Use / Function Calling**: 모델이 외부 함수·API를 호출해 작업을 수행하는 능력.
- **Fine-tuning**: 사전학습된 모델을 특정 데이터셋으로 추가 학습시켜 특화하는 과정.
- **No-code / Low-code**: 코드 생성 없이(혹은 최소한의 코드로) 시각적 설정만으로 앱을 만드는 방식 — 바이브 코딩과는 다른 카테고리.
- **Boilerplate**: 반복적으로 쓰이는 정형화된 코드 템플릿.
- **Technical Debt (기술 부채)**: 빠른 구현을 위해 미뤄둔 구조적 보완 작업이 누적된 상태.
- **CI/CD**: 코드 변경을 자동으로 통합(Continuous Integration)하고 배포(Continuous Deployment)하는 파이프라인.
- **Continuous AI / Agentic CI**: 백그라운드 에이전트를 CI처럼 상시 가동해 코드 품질을 관리하는 개념.
- **Feature Spec (기능 명세서)**: 구현할 기능의 요구사항·조건·예외 케이스를 정리한 문서.
- **User Story (유저 스토리)**: "~로서, ~하고 싶다, 왜냐하면 ~"형식으로 사용자 요구를 서술한 문서.
- **API**: 서로 다른 소프트웨어가 데이터를 주고받기 위한 규약.
- **Auth (인증/인가)**: 사용자가 누구인지 확인(인증)하고 무엇을 할 수 있는지 결정(인가)하는 과정.
- **Database (DB)**: 데이터를 구조화해 저장·조회하는 시스템.
- **Runtime**: 코드가 실제로 실행되는 환경.
- **Framework**: 개발의 공통 구조를 제공해 반복 작업을 줄여주는 코드 뼈대.
- **Client-Server Architecture**: 요청하는 쪽(클라이언트)과 처리·응답하는 쪽(서버)으로 역할을 나누는 구조.
- **Latency (레이턴시)**: 요청부터 응답까지 걸리는 지연 시간.
- **Live Share / Real-time Sync**: 여러 사용자가 동시에 같은 데이터를 보고 편집할 수 있게 하는 실시간 동기화 기능.
- **LLM (Large Language Model)**: Claude, GPT 등 바이브 코딩 툴의 엔진이 되는 대규모 언어모델.
- **Skill**: 에이전트에게 특정 작업 수행 방법을 패키지로 제공하는 지침 모음.
- **AI Builder**: AI를 활용해 실제 프로덕트를 만들어내는 사람 — 단순히 "AI로 코드를 생성해본 사람"과는 구분됨.
- **Loop Engineering**: 에이전트의 실행-검증-수정 루프 자체를 설계·개선하는 작업.
- **Prompt Management**: 프롬프트를 버전 관리하고 배포하는 체계 — 코드 재배포 없이 프롬프트만 수정해 하니스를 고칠 수 있게 함.

# 3. 강의데시벨 MVP 프롬프트 작성 (AS-IS / TO-BE)

## AS-IS

```
강의데시벨이라는 서비스를 만들고 싶어.
시각장애 대학생들이 강의자료(PPT, PDF) 안에 있는 표나 그래프 같은 걸
이해할 수 있게 AI가 대신 설명해주는 서비스야.

교수가 자료를 올리면 AI가 분석해서 설명을 만들어주고,
필요하면 사람이 검수도 할 수 있게 해줘.

MVP로 빠르게 만들어줘.
```

**문제점**: 사용자 역할(교수/학생/튜터) 구분 없음, 구체적 플로우(변환→판정→검수→제공→제보) 부재, 업로드 시점별 처리 로직 없음, 채널(CMS/자체사이트/LMS) 우선순위 없음, 확장성·데이터 설계 요구 없음, 검증 지표 없음.

## TO-BE (구조화된 프롬프트)

```
강의데시벨 MVP를 만들거야.

[배경]
첨부한 최종 제안서를 참고해. 핵심 문제는 Access Lag(자료 제공 시점과
실제 접근 시점 간 격차)와 Dependency(교육지원인력의 가용성에 좌우되는
의존성)이고, 이 두 가지를 해소하는 게 서비스의 존재 이유야.

[사용자 역할 3가지]
- 교수자: 기존 방식대로 자료를 업로드하는 사람
- 시각장애 학습자: 변환된 자료를 스크린리더/점자 환경에서 확인하는 사람
- 전공 튜터: 고위험 자료를 검수하는 사람

[핵심 서비스 플로우 — 이 순서와 로직을 그대로 구현해]
1. AI 1차 변환: 업로드 시 표·그래프·수식·다이어그램을 분석.
   기존 DB와 슬라이드 단위로 비교해 검수 이력 있으면 재사용,
   신규/변경 슬라이드만 변환. 업로드 후 10분 이내 1차 제공 목표.
2. 위험도 자동 판정: 낮음(자동 게시) / 중간(우선순위 검수 대상) /
   높음(튜터 필수 검수 대상) 3단계로 분류.
3. 학생 뷰어 반영 — 업로드 시점에 따라 제공 방식이 달라져야 해:
   - 수업 24시간 이전 업로드 → 전체 검수 완료 후 제공
   - 30분~24시간 이전 업로드 → 고위험 페이지부터 순차 검수,
     완료/미완료 상태 표시
   - 30분 이내 업로드 → AI 변환본 우선 제공, 미검수 상태임을 명시
4. 오류 제보 및 재검수: 학생이 페이지 단위로 오류 제보 →
   위험도 판정 단계로 재전달 → 우선순위 재조정 → 튜터 재검수 →
   즉시 반영. 반복 오류 유형은 DB에 축적.

[채널 우선순위]
MVP는 CMS 버튼형(기존 학교 LMS 등록 절차에 연동 버튼 추가)을
1순위로 구현하고, 자체 사이트형(직접 업로드)을 보조 채널로 붙여.
LMS 연동형(기관별 API 연동)은 이번 MVP 범위에서 제외하되,
추후 확장 가능하도록 업로드 인터페이스를 채널 독립적으로 설계해.

[데이터 설계]
슬라이드/페이지 단위로 검수 이력(위험도, 검수자, 검수 시각, 오류
제보 이력)이 유실되지 않도록 데이터 엔티티를 먼저 설계하고 보여줘.
추후 기관별 LMS 연동, 교과목·학기 단위 통계가 붙을 수 있도록
확장 여백을 둬.

[기술 제안 요청]
표/그래프/수식/다이어그램 인식이 가능한 멀티모달 AI 분석 파이프라인과,
스크린리더·점자 디스플레이 호환이 되는 학생 뷰어 프론트엔드,
검수 상태(대기/진행/완료)를 실시간으로 반영하는 구조를
각각의 근거와 함께 제안해줘.

[검증 지표 — KPI]
업로드→1차 제공까지 소요 시간, 위험도별 검수 완료율,
오류 재제보율, 수업 시작 전 완료율 등 서비스 운영에 필요한
지표도 함께 설계해.

[산출물 규칙]
develop 브랜치에 v0.1.0으로 기능 단위로 나눠 커밋하고,
핵심 설계 결정사항(AI 변환 엔진 선택, 위험도 판정 임계값,
뷰어 아키텍처)은 AskUserQuestion으로 확인받은 뒤 진행해.
```

**TO-BE 프롬프트가 개선한 점**: 제안서의 숫자·조건(10분, 24시간/30분 분기, 3단계 위험도)을 그대로 요구사항화 → 역할·데이터 엔티티·확장성을 먼저 고정 → 기술 선택은 AI에게 "근거와 함께" 위임 → 결정 지점에서 사람이 확인하는 체크포인트 삽입.
